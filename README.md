# Мини-CRM «Объекты и задачи»

Небольшая CRM для строительной компании: постановщик ставит задачи по объектам (стройкам),
исполнители выполняют их и отдают на проверку.

**Стек:** React 19 + TypeScript + Vite, Supabase (PostgreSQL, Auth, RLS), react-router.

## Как запустить

1. Создайте проект в [Supabase](https://supabase.com) (бесплатный тариф).
2. **SQL Editor** → выполните `supabase/migrations/20261103000001_init.sql`
   (или `supabase db push`, если используете Supabase CLI).
3. **Authentication → Sign In / Providers → Email** — выключите *Allow new users to sign up*
   (открытая регистрация отключена).
4. **Authentication → Users → Add user → Create new user** — создайте трёх пользователей
   (галочка *Auto Confirm User*):
   `manager@mini-crm.test`, `ivanov@mini-crm.test`, `petrov@mini-crm.test`.
5. **SQL Editor** → выполните `supabase/seed.sql` — проставит роли и создаст 3 объекта и 6 задач в разных статусах.
6. Локально:
   ```bash
   cp .env.example .env      # вставьте URL проекта и anon public key (Project Settings → API)
   npm install
   npm run dev
   ```
7. Деплой на Vercel: импортируйте репозиторий, добавьте переменные `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`.

## Структура

```

supabase/seed.sql      тестовые данные

```

## Как устроена безопасность

Все правила — в базе, интерфейс только показывает доступные кнопки.

| Что | Как защищено |
|---|---|
| Исполнитель видит только свои задачи | RLS на `tasks`: `is_manager() or assignee_id = auth.uid()` |
| Исполнитель видит только «свои» объекты | RLS на `objects`: есть хотя бы одна его задача на объекте |
| Создавать/править/удалять объекты и задачи | RLS: только `manager` |
| Переходы статусов | Единственный путь — функция `change_task_status()`; прямой `UPDATE status` блокирует триггер. Функция проверяет таблицу переходов и роль, для «На доработку» требует комментарий |
| История нельзя подделать | У `task_history` нет политик и прав на insert/update/delete для `authenticated`; записи пишут только серверные функции. Автор и время берутся из `auth.uid()` и `now()` |
| Роль нельзя повысить себе | Нет прав на изменение `profiles` через API |
| Анонимный доступ | У `anon` отозваны все права на таблицы и функцию |
| Секретные ключи | Во фронтенде только `anon` ключ; `service_role` нигде не используется; `.env` в `.gitignore` |

Проверка: правила тестировались прямыми SQL-запросами от имени разных ролей
(чужая задача, пропуск статуса, принятие своей задачи исполнителем, запись в историю, анонимный доступ) — всё отклоняется базой.
