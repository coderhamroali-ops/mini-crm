# Решения и допущения

Что я решил сам там, где ТЗ не даёт однозначного ответа:

1. **Роли хранятся в таблице `profiles`** (manager / executor). Роль назначает администратор в базе; через API её изменить нельзя.
2. **Исполнителем можно назначить только пользователя с ролью «исполнитель».** Постановщик не может назначить задачу себе или другому постановщику (проверка триггером).
3. **Постановщик может переназначать исполнителя и редактировать задачу в любом статусе**, но статус меняет только по правилам (принять / вернуть с проверки). Статус и история при переназначении сохраняются.
4. **Исполнитель не редактирует поля задачи** — только меняет статус по допустимым переходам.
5. **Удаление объекта удаляет все его задачи и их историю** (с подтверждением в интерфейсе). Удалять может только постановщик.
6. **Принятая задача — финальный статус**, дальнейших переходов нет (по таблице ТЗ).
7. **Имена пользователей видны всем вошедшим** — нужно, чтобы показывать автора и исполнителя. Email и прочие данные не показываются.
8. **Смена статуса сделана одной серверной функцией** (`change_task_status`), чтобы проверка перехода, смена статуса и запись в историю происходили атомарно, в одной транзакции.
9. **«Мои задачи»** сортируются так, чтобы сверху были задачи, требующие действия: «На доработке», затем «Новая», «В работе».

Что не успел / можно улучшить:

- Нет поиска и фильтров по статусам в списках.
- Нет пагинации — для тестового объёма данных не нужна.
- Нет realtime-обновлений: после действий страница перечитывает данные.
- Нет автотестов на фронтенде; политики проверены SQL-запросами вручную.
